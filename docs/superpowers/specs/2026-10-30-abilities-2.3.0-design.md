# divi5-builder 2.3.0: site management and the risky switches

Release 3 of issue #32. This document extends the master design (`2026-10-28-abilities-design.md`) and the 2.2.0 design (`2026-10-29-abilities-2.2.0-design.md`). Where they differ, this one wins for 2.3.0. Everything already built stays: the switch store, the audit log, the change history, the confirmation codes, the secret filter, the one rule.

## Intent

2.1.0 gave AI clients eyes, 2.2.0 gave them hands for content. 2.3.0 gives them the site's settings and appearance: site options, the homepage, theme settings, Custom CSS, widgets, the caches, scheduled tasks, and (on block themes) templates and global styles. These are the things an owner changes a few times a year and an AI assistant is asked about when something looks wrong: "the site title has a typo", "set the new landing page as the homepage", "the footer widget still shows last year's hours", "clear the cache", "that stuck cron job".

Most of these are reversible by nature (an option has an old value; a theme mod has an old value). A few can take a site down (a bad Custom CSS rule hides the page; a wrong homepage setting; a cron job that runs a migration). Those are the first **risky actions**, which the master design puts behind a second switch per category, off by default, with a plain risk note.

The maintainer opted out of the brainstorm questions for this release ("you know the work we do"); the choices below are the author's, made from the master design and the work done on client sites.

## The one rule still holds

Every write in 2.3.0 is recorded in the change history with the full previous value, so it can be put back by hand:

- an option: the old value;
- a theme mod: the old value (or "absent");
- Custom CSS: the whole previous stylesheet;
- a widget change: the whole `sidebars_widgets` map plus the widget's previous instance;
- a template or global styles: the previous content, with a WordPress revision where one exists;
- a cache flush and a cron run: a row that says what ran (nothing to put back).

No permanent delete exists in 2.3.0 except **removing a widget** and **deleting a theme mod**. Both keep the full previous value in the history, both are reversible by setting it again, and WordPress has no trash for either, so they are treated as normal writes (not the two-step delete): the history row IS the copy. This is the author's call; the master design's "Deleting" section lists neither.

## Goals

- The "normal writes" and "risky actions" of the master design's Categories table for Settings, Templates and global styles, Appearance, Widgets, Cache and Site health/cron, as abilities.
- The risky-switch plumbing: store, registration gate, permission re-check, settings UI with risk notes, tests.
- The reuse rule: the cache flush calls the Updates part's `wpsu_clear_caches()`; nothing is duplicated.
- A live run on the maintainer's dev site that changes and restores a setting, a theme mod, Custom CSS and a widget, flushes the caches, runs a harmless cron event, sets the homepage to a test page and back.

## Non-goals

- Users, plugins, themes, core updates, email (2.4.0).
- A settings "undo" ability (history plus hand restore, as in 2.2.0).
- Editing arbitrary options (`options-set` with any key): never. Only the allow-list below.
- The error log: read only (no clear).
- Server-level things (PHP settings, wp-config, files): never, per the maintainer's 2026-10-28 decision.

## Anti-goals

The master design's anti-goals, plus:

- A risky action reachable while its risky switch is off, through any route.
- A write to `siteurl` or `home` (it can lock everyone out). These are never writable.
- A homepage setting that points at a page that does not exist, is not published, or is not a page.
- Custom CSS saved without the previous stylesheet in the history.
- A cron run of a hook that is not actually scheduled (arbitrary action execution).

## Switches

### The risky switch

- The store already holds `risky_on` per category (2.1.0 laid it down, fail-closed). 2.3.0 starts using it.
- **Registration gate:** an ability marked `risky => true` in its definition is registered only when the master, the category AND the category's `risky_on` are all on. The run wrapper and the permission callback re-check all three, as they do for the category.
- **Settings UI:** under each category that has risky actions in this release (Settings, Templates and global styles, Appearance, Site health and cron), a second checkbox "Also allow risky actions" with a plain risk note. All off by default. The notes:
  - **Settings:** "Can change the homepage, permalinks, time zone and whether search engines index the site. A wrong value is easy to put back from the change history, but visitors see it in the meantime."
  - **Templates and global styles:** "Changes the theme's templates and global styles on block themes. A broken template can blank a page until it is put back."
  - **Appearance:** "Can change Custom CSS and theme settings. A wrong CSS rule can hide the whole page until it is put back."
  - **Site health and cron:** "Can run a scheduled task now. Tasks belong to plugins and may do real work (send emails, process orders, run migrations)."
- Widgets and Cache have no risky actions; their writes are normal.
- **The upgrade-consent step is repeated** (author's call, from the builder check): the normal writes in Settings, Appearance, Widgets and Cache go live on update on any site whose master switch is on, and the note the admin agreed to in 2.2.0 spoke of content, not settings. So the schema version goes to `'3'`, and the move from `'2'` to `'3'` on a site with the master on turns the master off once (network-wide on multisite, as 2.2.0 does) with the notice: "divi5-builder 2.3.0 adds AI abilities that can change site settings, theme settings, widgets and caches, and risky actions behind their own switches. The AI abilities master switch was turned off during the update; review the switches and turn it on again when you are ready." Every new risky switch starts off.
- The static scan rule stays: only the switch files write the switch option.

### Overlap with the Updates part (the maintainer's question, 2026-10-30)

The Updates part has two layers: the **engine** in the plugin (`parts/updates.php`: status, update one item, clear caches, behind the Updates switch) and the **choreography** in the skill (`scripts/site-care/site-updates.js`: snapshot pages, show the plan, wait for a go, update, re-check). The abilities reuse the engine and never duplicate it: the 2.1.0 reads already call it; 2.3.0's `cache-flush` calls `wpsu_clear_caches()`; 2.4.0's update abilities will call `wpsu_update()`. Whether the REST route and the script stay as a second door, or retire in favour of the abilities once those carry the choreography server-side, is decided in the 2.4.0 design. 2.3.0 changes nothing there.

## Abilities

Names follow the earlier releases. Capabilities: `manage_options` for settings, appearance, templates, cache and cron; `edit_theme_options` for widgets and Custom CSS (core's own rule for Custom CSS is `edit_css`, which maps to `unfiltered_html` by default; use `edit_css`). On multisite, `health` and `cache` also need `manage_network` (as the 2.1.0 reads do); the others are per-site settings and need the per-site capability only.

### Settings

| Ability | Risky | Input | Notes |
|---|---|---|---|
| `settings-set` | one normal definition; the handler refuses risky keys while the switch is off | `settings`: an object of key => value, at least one key | Normal keys: `blogname`, `blogdescription`, `date_format`, `time_format`, `start_of_week`, `posts_per_page` (the plugin keeps it to 1 to 100; core would accept any whole number), `default_comment_status`. Risky keys: `timezone_string`, `gmt_offset`, `WPLANG` (must be an installed language), `permalink_structure` (flushes rewrite rules afterwards), `blog_public`. One call may mix normal and risky keys; if any key is risky and the risky switch is off, the whole call is refused `not_allowed` and nothing is written. As built, `settings-set` is ONE ability registered whenever the Settings category is on (it is not marked `risky`, since most calls are normal); the refusal of risky keys is made inside the handler, which reads the risky switch itself, so the ability cannot be reached with a risky key by any route while the switch is off. Unknown keys and `siteurl`, `home`, `admin_email` are refused `invalid_input` with the allow-list in the message. Values are validated as core's Settings API does (`sanitize_option`); a value core rejects answers `invalid_input` with core's message. History: one row per call, `before` = the old values of the keys given. |
| `settings-set-homepage` | risky | `show_on_front` (`posts` or `page`), `page_on_front`, `page_for_posts` | Pages must exist, be published and be of type `page`; `page_on_front` and `page_for_posts` must differ; the Pages category must be on (strictest switch wins). History before = the three old values. |

### Templates and global styles (block themes only)

On a classic theme (every Divi site) these answer `{ is_block_theme: false, note }` and write nothing, as the 2.1.0 reads do.

| Ability | Risky | Input | Notes |
|---|---|---|---|
| `templates-update` | risky | `id` (the template or part id as `templates-list` returns it), `content`, `expect_hash` | Content is block markup; needs `unfiltered_html`; `expect_hash` = md5 of the stored content (the theme-file fallback counts as content with its own hash). A theme-file template becomes a customised `wp_template` post, as the editor does. History before = previous content (full). |
| `global-styles-set` | risky | `styles` (JSON object), `expect_hash` | Writes the **user layer only** (the active theme's `wp_global_styles` post), never the merged data: writing the merged JSON back would copy the theme's defaults into the user layer and stop theme updates showing through. `global-styles-get` therefore gains a `user` object (the user layer as stored) and `user_hash` = md5 of that stored JSON; `expect_hash` is checked against it. The write replaces the user layer with `styles` after core's sanitising. As built: the document is put together as core's global styles controller does (`prepare_item_for_database`: styles, settings, the user flag, schema version), and then cleaned as core's kses filter `wp_filter_global_styles_post` cleans it (the user flag taken out, `WP_Theme_JSON::remove_insecure_properties()`, the flag put back), always, whoever the caller is. It replaces the user layer whole: keys left out are dropped (core's own endpoint merges them); the final review wave may change this. History before = the previous user layer. |

### Appearance

| Ability | Risky | Input | Notes |
|---|---|---|---|
| `appearance-theme-mod-set` | risky | `name`, `value` | Theme mods of the active theme. The name must be plain ASCII (the 2.2.0 key rule) and not secret-named; a mod whose current value holds a secret-named key cannot be overwritten (2.2.0 rule). `nav_menu_locations` is refused here (menus have their own ability). `custom_css_post_id` and `sidebars_widgets` are refused (internal). Value: scalar or JSON-safe array. History before = old value or `absent: true`. |
| `appearance-theme-mod-delete` | risky | `name` | Same rules; the history row holds the full old value. Not a two-step delete: the row is the copy and the value is one `theme-mod-set` away. |

Theme mods are risky, matching the master design's table and the Appearance risk note (the author's first draft had them normal; the builder check caught the contradiction). **Divi's own Theme Options** (the `et_divi` option: logo, header, colours and the rest) are **out of scope** for 2.3.0 (author's call): they are hundreds of keys with Divi-specific validation, and the work on the maintainer's sites goes through the design system and the pages, which already have abilities. A follow-up issue records it.
| `appearance-custom-css-set` | risky | `css`, `expect_hash` | Core's Additional CSS for the active theme through `wp_update_custom_css_post()`, needs `edit_css`; `expect_hash` = md5 of the current stylesheet (as `appearance-get` returns it, which gains `custom_css_hash`). There is **one store**: Divi sends its Theme Options Custom CSS into core's Additional CSS on WordPress 4.7+, and the plugin's existing `POST /custom-css` route writes the same post, so there is no `target` input and no route refactor (the builder check caught this). The route keeps its own behaviour (append mode, empty refused); the ability is a plain replace, and an empty `css` is allowed (restoring to nothing is a valid restore). Size cap 256 KB. The CSS is stored as given (CSS is not HTML; no kses), after `[redacted]` and `</style` checks (`masked_read`; `invalid_input`). History before = the whole previous stylesheet. |

### Widgets

Block widgets (WordPress 5.8+) and classic widgets both live in `sidebars_widgets` plus per-type option arrays (`widget_block`, `widget_text`, …). The abilities work at that level through core's functions (`wp_get_sidebars_widgets`, `wp_set_sidebars_widgets`, `get_option( 'widget_<type>' )`), the same model core's widgets REST controller uses.

| Ability | Risky | Input | Notes |
|---|---|---|---|
| `widgets-add` | normal | `sidebar`, `type` (a registered widget id base, e.g. `block`, `text`), `settings` (the instance: for `block`, `{ content }` holding block markup), optional `position` | Registered sidebar and widget type only; the instance goes through the widget's own `update()` sanitiser (`WP_Widget::update`) when the type is a `WP_Widget`; a `block` widget needs `unfiltered_html` when its content holds blocks that core would strip. Returns the new widget id (`type-N`). |
| `widgets-update` | normal | `id`, `settings` | Same sanitising. History before = the old instance. |
| `widgets-move` | normal | `id`, `sidebar`, `position` | Including to `wp_inactive_widgets`. History before = the whole `sidebars_widgets` map. |
| `widgets-remove` | normal | `id` | Removes the widget from its sidebar and deletes its instance. History before = sidebar, position and the full instance (the copy). Not a two-step delete, by the same reasoning as theme mods. |

A widget instance that holds a value under a secret-named key cannot be updated or removed (2.2.0 rule).

### Cache

| Ability | Risky | Input | Notes |
|---|---|---|---|
| `cache-flush` | normal | none | Calls `wpsu_clear_caches()` (the Updates part's function; the ability does not need the Updates switch, the function is shared code). Returns what was flushed. History row: action `flush`, before = the detection result. Needs `manage_options` (+ `manage_network` on multisite). |

### Site health and cron

| Ability | Risky | Input | Notes |
|---|---|---|---|
| `cron-run` | risky | `hook`, `timestamp`, `schedule` (as `cron-list` returns them; `schedule` may be empty for a single event), optional `args_key` (the event's args key from `cron-list`, which now returns it; named `args_key` and not `key` because `key` is a secret name to the scrubber and the history filter, which would drop it) | Exactly one scheduled event is identified; a hook that is not scheduled is refused `not_found` (never an arbitrary action); several events with the same hook and time and no `args_key` are `ambiguous`; hooks whose name starts with `d5b_` are refused, and so are core's lifecycle hooks (`muplugins_loaded`, `plugins_loaded`, `setup_theme`, `after_setup_theme`, `init`, `wp_loaded`, `rest_api_init`, `admin_init`, `wp`, `parse_request`, `send_headers`, `template_redirect`, `shutdown`), which run on every request and are never a task. The run mirrors `wp_cron()` for one event, in this order: take core's `doing_cron` lock (refuse with `unavailable` if WP-Cron holds a fresh one; the lock is read fresh, past this request's caches, as `wp-cron.php` does, both when it is taken and before it is released, and is released only while it is still ours), **reschedule or unschedule first** as core does, then `do_action_ref_array( $hook, $args )` in the request with `wp_doing_cron` true and its output buffered (counted as `output_bytes`, never sent), then release the lock. The history row is written before anything changes; when it cannot be, nothing runs (`history_unavailable`). PHP cannot interrupt a running hook, so the "time budget" is **measure and report**: `set_time_limit( 60 )` as a best effort, the duration measured, and `over_budget: true` when it passed 20 s; a fatal inside the hook is caught by a shutdown handler that marks the audit and history rows `fatal` (the schedule is already correct because it was adjusted first). Returns `ran`, `hook`, `duration_ms`, `rescheduled`, `unscheduled`, `over_budget` and `output_bytes`. History row: action `run`, before = the event as listed. |

`error-log` stays read-only. `health-status` stays read-only.

## Guardrails (additions)

12. **Risky actions** register only with the risky switch on and re-check it at permission time and in the run wrapper.
13. **`siteurl` and `home` are never writable**, by construction (not in the allow-list) and by a test.
14. **Options are validated with core's own `sanitize_option()`** so a value that would break the admin UI is refused the same way wp-admin refuses it.
15. **Homepage changes check the pages** exist, are published pages, and differ.
16. **Cron runs only scheduled events**, identified exactly, with the time budget and the rescheduling core does.
17. **Secret rule** (2.2.0): theme mods, widget instances and settings values under secret-named keys are refused for overwrite or removal.

## Tests

The 2.2.0 test list applies to every write (history row with a rebuildable before, strictest switch, capability matrix, secret rule, hostile input, mutation checks), plus:

- Risky gate: for each risky ability, category on + risky off = not registered and refused on direct run; risky on = registered; master off = nothing.
- `settings-set`: allow-list by construction (a test asserts `siteurl`, `home`, `admin_email`, `users_can_register`, `default_role` are refused); mixed normal+risky with risky off refuses the whole call; `sanitize_option` refusals pass through as `invalid_input`; `permalink_structure` flushes rewrite rules; `WPLANG` must be installed.
- Homepage: missing page, draft page, a post id, same page for both: all refused; success writes three options and one row.
- Custom CSS: hash required; `</style` refused; 256 KB cap; an empty stylesheet is a valid write; the existing route is untouched.
- Widgets: a text widget's `update()` sanitiser is applied; a block widget with `<script>` from a user without `unfiltered_html` is refused; move to inactive and back; remove keeps the full instance; the sidebars map in before can rebuild the layout.
- Cron: an unscheduled hook refused; a `d5b_*` hook refused; the lock is taken and released; a single event is unscheduled and a recurring one rescheduled BEFORE the hook runs; a slow hook reports `over_budget`; a hook that fatals leaves rows marked `fatal`.
- Cache: `wpsu_clear_caches` is called once; the Updates switch is NOT required.
- Live script `scripts/abilities-live-site.js <site> <step>` (exit 0 passed, 1 unexpected status or missing history row, 2 usage or a non-`d5b-live-` page, 3 the homepage plan waits for `--confirm go`): `settings` (change `blogdescription` and put it back, both through the ability; read the history row), `homepage --page <id> --confirm go` (risky; set to a `d5b-live-` page the maintainer nominates and back, with the maintainer's go; without `--confirm go` it prints the plan and changes nothing), `theme-mod` (set and delete a `d5b_live_mod`), `css` (append a `/* d5b-live */` comment and restore the previous stylesheet from the response), `widget` (add a text widget to the first sidebar, update, move to inactive, remove), `cache`, `cron` (risky; run `wp_privacy_delete_old_export_files`), `history`. Touches only `d5b-live-`/`d5b_live_` things and restores every value it changed.
