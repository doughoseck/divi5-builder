# divi5-builder 2.2.0: content writes, Divi writes and the change history

Release 2 of issue #32. This document extends the approved design in `2026-10-28-abilities-design.md` (the master design) with the decisions taken on 2026-10-29. Where the two differ, this one wins for 2.2.0. Everything the master design says about switches, the audit log, the secret filter and the guardrails still applies.

## Intent

2.1.0 gave AI clients eyes on a site. 2.2.0 gives them hands for content: creating and changing posts, pages, custom items, blocks, media, terms, comments, custom fields and menus, restoring revisions, the Divi writes the skill already performs over REST, and one new small Divi edit meant for a phone. Every write is recorded in a change history that holds enough to put it back.

The maintainer runs many WordPress sites for clients and does varied work on them: content, comments, menus, Divi pages. There is no single first job. The release is a general set of hands, with one rule above all others.

## The one rule: everything can be undone

The maintainer, 2026-10-29: the only thing that would make them wince is deleting something that cannot be put back. People and AI both make mistakes; as long as a mistake can be undone, that is fine.

So, for every write ability in 2.2.0:

- **Trash, never delete,** wherever WordPress can trash. There is no empty-trash ability.
- **A permanent delete only after confirmation,** through the two-step preview and confirmation code in the master design ("Deleting"), and only for things WordPress cannot trash.
- **The change history keeps the full "before"** of every write, for 30 days (see "Change history"). Not the changed fields only, as the master design said: a capped copy of a Divi page is a page you cannot put back.
- **No stale overwrite:** every update of content carries `expect_hash` (the master design's guardrail 2).
- **A masked read is never written back:** if the get that produced the content returned `masked: true`, an update with that content is refused with `masked_read`, so a hidden key is never overwritten with `[redacted]`.

There is **no revert ability** in 2.2.0 (the maintainer's call, 2026-10-29). Undo is done by a person: from WordPress's own revisions where one exists, or from the full copy in the history row. The desktop skill also keeps its habit of saving a copy locally before any permanent delete.

## Goals

- Every "normal write" in the master design's Categories table for the content categories (Posts, Pages, Media, Taxonomy, Comments, Custom fields, Custom post types, Blocks, Menus, Revisions), as abilities.
- The two-step delete for terms, whole menus and meta keys (the content things WordPress cannot trash), and for media when `MEDIA_TRASH` is off.
- The Divi writes: builder mode, canvas link, design-system writes, Theme Builder layout write and restore, the section-level page edit, and the new text edit.
- The change history: table, rows for every write, the wp-admin list, and the `history-changes-list` and `history-change-get` abilities.
- A live run on the maintainer's dev site that creates, changes, trashes and (with the maintainer's confirmation) permanently deletes test items, and leaves the site as it was.

## Non-goals

- Settings, templates, global styles, appearance, Custom CSS, widgets, cache, health, cron (2.3.0). Users, plugins, themes, core, email (2.4.0).
- A revert ability.
- Bulk operations. One object per call; a client that wants ten changes makes ten calls, each logged.
- Running the `divi.js` compiler or the catalogue lint on the server. The compiler stays in the skill.
- Phone transport (#49).

## Anti-goals

The master design's anti-goals, plus:

- A write that changes content the client did not read (no `expect_hash`, or a wrong one, must never write).
- A permanent delete without a valid confirmation code.
- A write with no change-history row, or a row from which the "before" cannot be rebuilt.
- A write that reaches a category whose switch is off (strictest switch wins, per object type, as 2.1.0 enforces).
- A publish nobody asked for.

## Switches

No change to the store. Writes come on with their category when the master is on, as the master design says ("normal writes are on by default with their category"). There is no separate "allow writes" switch in 2.2.0: the master starts off, every write is logged, and every write can be undone. The risky switches are not yet shown, because 2.2.0 has no risky actions except permanent deletes, which are gated by the confirmation code rather than a switch (the master design's "Deleting").

The risk note under the master switch gains one sentence: "With this on, connected AI clients can also create and change content in the categories you tick. Every change is kept in the change history for 30 days."

## Abilities

Names follow 2.1.0: `divi5-builder/<category>-<action>`. Every write ability sets `meta.annotations` truthfully: `readonly => false`, `destructive => true` only for trash and permanent delete, `idempotent` as appropriate. Every write needs the same per-object capability WordPress needs in wp-admin.

### Posts, pages, custom post types, blocks

Four shapes, applied to `posts-*`, `pages-*`, `cpt-*` (with `type`) and `blocks-*`:

| Ability | Input | Notes |
|---|---|---|
| `*-create` | title, content, status (`draft` default), excerpt, slug, parent, author, categories/tags or terms, meta (non-protected keys), featured image id | **Status defaults to `draft`.** `publish`, `future` (with a date) and `private` are accepted only when given explicitly and the caller has `publish_posts` for the type. Returns id, url and hash. |
| `*-update` | id, `expect_hash`, plus any of the create fields | `expect_hash` is required whenever `content` is in the input. Title-only or status-only updates do not need it. A Divi page (`_et_pb_use_builder = on`) with `content` in the input is accepted with the hash, and the description says to prefer `divi-section-edit` or `divi-text-edit`. WordPress makes a revision as usual. |
| `*-trash` | id | One step. Returns the id and `restore_with`. |
| `*-restore` | id | From trash, **back to the status it had before** (WordPress keeps it in `_wp_trash_meta_status`; since 5.6 a plain untrash gives `draft`). Undoing a trash is not a publish nobody asked for: it puts back what was there. |

**Divi content and `unfiltered_html`** (my call, from the builder check): when the incoming content contains Divi blocks (`<!-- wp:divi/`), `*-create`, `*-update`, `revisions-restore`, `divi-section-edit` and `divi-text-edit` refuse with `needs_unfiltered_html` for a caller without that capability, exactly as the Theme Builder route does today, because kses would corrupt the block JSON and the corrupted page would become the next "before". Plain content is not affected.

**Builder flags on create** (my call): `*-create` and `*-update` accept `divi: true`, which sets `_et_pb_use_builder = on` and `_et_pb_use_divi_5 = on` together, the same pair `link-canvas` sets. Without it, content that holds Divi blocks is still saved but the description warns it will not render as Divi until `divi-builder-mode` is on.

`cpt-*` keeps the 2.1.0 refusal of internal types and of post, page, attachment and wp_block. Blocks (`wp_block`) are plain posts to WordPress, so the same shapes apply; `blocks-update` carries `expect_hash` like the others.

### Revisions

`revisions-restore` with `post_id`, `revision_id`, `expect_hash` (the hash of the post's current content). Needs `edit_post`. Core's `wp_restore_post_revision()` updates the post with `wp_update_post()`, and the revision that update makes holds the RESTORED content, not the content it replaced. The replaced content is in the revision made at the post's own last save, when there is one: the history row points at that revision when its content is byte-identical, and always keeps the replaced content in `before` as well, because revisions can be pruned.

#### `divi-section-edit`

A PHP port of `blocks.js`: parse the stored content into the block tree, resolve `at`, check that `with` parses and is the same kind as what it sits next to (section beside section, module beside module, and for `append` the kind a child of `at` has), splice, parse the result again, and write only if it parses. Everything outside the addressed block stays byte for byte. The response returns the new hash and the `tree` of the page (addresses and labels), so the next edit needs no separate get. Ambiguous `label:` or `#id` addresses are refused with the candidates listed.

#### `divi-text-edit`

The phone edit. Changes words inside existing modules without touching layout.

- Input: `post_id`, `expect_hash`, `old` (exact text, 1 to 2000 characters), `new` (0 to 2000 characters), optional `at`.
- It searches the **text a visitor would read**: the text content of module attributes that hold text (heading, text, button label, blurb title and body, and the other text-bearing fields the catalogue knows), inside the addressed block or the whole page. Those fields hold HTML (`Open <strong>Mon to Fri</strong> 9 to 5`, `&amp;`, `<br>`). The search runs over the visible text of each field, with tags removed and entities decoded; the replacement is made in the field's HTML.
- **Matches that cross markup** (my call, from the builder check): when the matched text lies inside one run of text with no tag inside it, it is replaced in place and the tags around it stay. When the match spans a tag (`old` = "Mon to Fri 9 to 5" against `<strong>Mon to Fri</strong> 9 to 5`), the ability refuses with `crosses_markup` and returns the field's stored HTML for that match, so the caller can either shorten `old` to one side of the tag or pass `html: true`, which matches and replaces against the stored HTML source instead. Nothing is ever silently dropped.
- `old` must occur **exactly once** in that text. Zero matches: `not_found`, with up to 5 near matches (same words, different case or spacing) in the response. More than one: `ambiguous`, with the address of each block that holds a match, so the caller can repeat with `at`.
- Divi stores module text JSON-encoded inside the block comment, with HTML entities and escaped quotes. The replacement is made in the decoded text and re-encoded the same way, so quotes, ampersands and non-ASCII characters round-trip. The result must parse, and a get of the page must show `new` where `old` was.
- It never changes attribute names, option values, class names, ids or anything outside text-bearing fields, even if `old` happens to match there.
- Response: new hash, the block address, and a 120-character excerpt around the change.

## Change history

- **Table** `{prefix}d5b_history`, created the same way as the audit table (write-ahead install from the abilities path, per site, dropped on uninstall with the version option). Columns: id, created_at (UTC), user_id, ability, audit_id (the audit row of the call), object_type, object_id, action (`create`, `update`, `trash`, `restore`, `delete`, `assign`, `reorder`, `upload`), before (longtext JSON), after (longtext JSON), revision_id (nullable), summary (varchar 191: one plain sentence, "Updated page 42 'Contact us'").
- **Before and after:** `before` is the **full** state needed to put the object back, after the secret filter's key removal (a secret under a secret-named key is never stored). For a post, page, custom item or block, `before` holds the fields other than content, and the previous content is kept like this: if a revision exists whose content is byte-identical to the previous content, `revision_id` points at it; otherwise (the first update of a post, revisions off or unsupported for the type, or the matching revision already pruned by `WP_POST_REVISIONS`) `before.content` holds the full previous content. The revision WordPress makes on the update itself holds the new content, never the old, so it is not what `revision_id` points at. The same holds for `revisions-restore`: the revision core makes holds the restored content, so `revision_id` points at the revision of the replaced content or, when there is none, is empty and `before.content` is the only copy. For everything WordPress does not version (terms and their assignments, menus with items and locations, meta values, media metadata, comment status and content, Divi design-system data, Theme Builder layouts, builder mode, canvas link), `before` holds the full copy. `after` holds the changed fields only. Rows are capped at 8 MB each; a copy that would exceed the cap is stored as `{ "too_large": true, "bytes": N }` and the write is still made and the row still written (the description of that ability says large content relies on WordPress revisions).
- **Written after a successful write,** in the same request. A write that cannot write its history row is still a write that happened; the audit row then carries status `ok_no_history`, and the plugin shows an admin notice when that has occurred in the last 24 hours. (Fail-closed is not possible here without transactions across tables; the audit row is the record that the write happened.)
- **Retention:** 30 days, pruned by the existing daily `d5b_audit_prune` event.
- **wp-admin:** a second read-only list under Settings > Divi 5 Builder next to the audit list, filterable by date, user and ability, showing summary, object and a link to WordPress's revision compare screen when `revision_id` is set. A row expands to show `before` and `after` as formatted JSON, with the secret filter's STRICT masking applied on display.
- **Abilities:** `history-changes-list` (filters: ability, user, since, object_type, object_id, per_page max 100, page) and `history-change-get` (id, returns the full row). Both need `manage_options`, read the current site's table only, and go through the result scrubber like everything else.

## Delete preview and confirmation

As the master design's "Deleting", with these details fixed:

- The code is 12 characters from `[A-HJ-NP-Z2-9]`, stored as a transient keyed on a hash of user id, ability, object and a fingerprint of the object's current state (for a term: name, slug, parent, count; for a menu: item ids and modified times; for meta: the value; for media: the modified time), valid 10 minutes, deleted on use.
- The preview response has `confirmation`, `expires_at` and a plain `message` that tells the AI, in one sentence, to show the preview to the user and wait for their explicit OK before calling the delete.
- The delete needs the same user, the same object, an unchanged fingerprint and an unused, unexpired code. Any mismatch returns `confirmation_invalid` with the reason (`expired`, `used`, `stale`, `wrong_object`, `wrong_user`), and nothing is deleted.
- The history row for a permanent delete is written **before** the delete, with the full copy; if that row cannot be written, the delete is refused with `history_unavailable`. This is the one place history is fail-closed, because there is nothing else to put the object back from.

## Guardrails (additions to the master design's list)

7. **Draft by default.** New content is a draft unless the caller asks for another status outright and may publish.
8. **Masked reads are not written back.** An update whose content came from a get that returned `masked: true` is refused with `masked_read`. The client cannot be trusted to tell us where content came from, so the check is: if the incoming content contains the literal `[redacted]` marker produced by the filter and the stored content does not, refuse.
9. **One object per call.** No list inputs of ids for writes, except `taxonomy-assign` (terms for one post) and `menus-reorder` (items of one menu).
10. **Writes respect the object's category switch,** by type, exactly as the 2.1.0 reads do: a page cannot be changed through `cpt-update`, `meta-set`, `taxonomy-assign` or `divi-*` when Pages is off.
11. **Nothing fetches the public internet except `media-upload` from a URL,** with the address checks above.

## Tests

The master design's test list applies. In addition:

- Restore from trash returns the previous status, not `draft`; `menus-item-restore` returns the item to its menu, parent and position.
- `before` holds the full previous content when no byte-identical revision exists (first update; revisions off; revision pruned).
- `divi-ds-restore` by `time` refuses when the backup list shifted; `/global-colors` is not registered as an ability.
- Divi-block content without `unfiltered_html` is refused on every content write path.
- For every write ability: the audit row, the history row, and that `before` is enough to rebuild the object (a test that deletes or changes, then recreates from the row, then compares).
- `expect_hash` missing or wrong refuses and writes nothing; the stored content is byte-identical afterwards.
- `masked_read` refusal.
- Draft by default; publish needs the capability.
- Strictest switch wins for every write path that touches a post-like object.
- The confirmation code: wrong user, wrong object, changed fingerprint, expired, reused.
- `divi-section-edit`: the same fixture set `blocks.js` uses, run through the PHP port, with byte-identical results for every operation and address form; refusals for a non-parsing `with` and a kind mismatch.
- `divi-text-edit`: round-trips of quotes, ampersands, `<br>`, non-ASCII and Divi variable tokens (`$variable(...)$`); zero and multiple matches; a match inside an attribute name or option value is not changed.
- `media-upload`: a private, loopback and link-local URL refused, redirects re-checked, size and mime caps.
- Mutation checks on every guard. An adversarial pass over the write path: stale hashes, confirmation codes, the text edit's encoder, the URL fetch, and the switch gate for writes.
- The 2.1.0 stand-ins extended so that `wp_register_ability` validates null input against the schema as core does (the follow-up from the 2.1.0 live run).

## Live run (the maintainer's dev site)

A script like `abilities-live-check.js` for writes, which only ever touches items it created and named `d5b-live-…`:

1. Master on, all categories. Create a draft post and a draft page, update each with the hash, update one with a wrong hash (refused), trash both, restore one, trash it again.
2. Upload a small image from a URL on the dev site itself, update its alt text, trash it (or preview the delete when `MEDIA_TRASH` is off; the maintainer confirms).
3. Create a tag, assign it to the test post, preview its delete, delete it with the maintainer's confirmation.
4. Create a menu, add two items, reorder, preview and delete it with the maintainer's confirmation.
5. On a copy of a Divi test page the maintainer nominates: `divi-text-edit` one heading, check the page in the Visual Builder, `divi-section-edit` replace one section with its own markup (a no-op splice), then restore the page from its revision.
6. Read `history-changes-list` and check every write has a row and every `before` is complete.
7. Master off. The maintainer empties the trash.
