# divi5-builder 2.4.0: users, plugins, themes, core and email

Release 4 of issue #32, the last of the four. This document extends the master design (`2026-10-28-abilities-design.md`) and the 2.2.0 and 2.3.0 designs. Where they differ, this one wins for 2.4.0. Everything already built stays: the switch store, the risky switch, the audit log, the change history, the confirmation codes, the secret rule, the write framework (`d5b_wc_*`).

## Intent

2.4.0 gives AI clients the maintainer's maintenance loop: see what is out of date, keep a copy of what is about to change, update, check the site, and put the old version back when an update goes wrong. Around it, the small user and email tasks that come up on every client site: a new administrator, a password reset, a test email.

The maintainer described the loop (2026-11-02): a snapshot of the versions before updating, the updates, a visual check of the site, and when something breaks either a fix on the new version or a rollback to the old one "if I can find and download it off the net". The last clause is the gap: premium plugins cannot be found on the net. 2.4.0 closes it by keeping the old copy itself.

## The one rule still holds

Every write in 2.4.0 is recorded in the change history with what is needed to put it back:

- a plugin or theme update: the previous version AND a copy of the previous folder, kept for 30 days in the same store as deleted media files (`wp-content/uploads/d5b-history/<row id>-<32 hex>/`);
- a plugin or theme rollback: the version being replaced and a copy of ITS folder (a rollback is itself undoable);
- activate, deactivate, switch theme: the previous state (the active plugin list, the previous stylesheet);
- install: the slug and version (undo = delete);
- delete: the slug, the version and a copy of the folder (undo = put the folder back by hand). A plugin delete runs the plugin's own uninstall routine as WordPress does (the maintainer's decision, 2026-11-02), and that data is gone for good: the preview says so, and `keep_data: true` gives the files-only delete that is fully undoable;
- a translations update: the one exception, no copy (language files, nothing to break); the row holds the count;
- a core update: the previous version only. WordPress keeps no old core and the plugin does not copy one; the response and the risk note say that a core rollback is a backup restore;
- a user: the user record without secrets (login, email, display name, roles, registration date, the non-secret meta) and, for a delete, who the content was reassigned to and the ids of the reassigned posts (so they can be moved back; WordPress does not reassign comments, they keep their author name);
- an email: a row saying what was sent to whom (nothing to put back).

## The human check is part of the contract

The maintainer's words: "there is no substitute for the human check and it only takes a few seconds". The plugin checks what a machine can check and then asks for the human one:

- Every update, rollback, activate, deactivate and theme switch result carries `pages` (the machine comparison, below) and `human_check`: a fixed sentence asking the user to look at the site in a browser and on a phone for layout breaks, missing images, console errors, broken forms and raw shortcodes, and saying that the machine check found nothing of that kind or cannot see it.
- The ability descriptions tell the AI to pass that request on to the user after the run, never to report the site as fine.
- The skill's update reference says the same.

## Goals

- The Users, Plugins, Themes, Core and Email rows of the master design's Categories table, as abilities, behind the master, the category and (for most of them) the risky switch.
- Old versions kept and restorable: `plugins-rollback`, `themes-rollback`.
- Page checks inside the plugin, so a phone gets the same before/after report the PC script gives today.
- A live run on the maintainer's dev site: install a small plugin from wordpress.org, activate, deactivate, update something real if an update is waiting (else skip with a note), roll it back, delete it with the preview and code; create a test user, reset their password, change their role, delete them with reassignment; send a test email to the maintainer; check the history.

## Non-goals

- Installing from anywhere but wordpress.org (the maintainer: "I upload premium zips myself"). No zip upload, no URL install.
- Setting or returning a password, ever. Password reset means sending WordPress's own reset link.
- Sending email to arbitrary addresses. The email ability sends only to people the site already knows.
- A core rollback.
- Rewriting the PC script (`scripts/site-care/site-updates.js`) to call the abilities. It keeps working against the REST route; the skill doc says which to use when. Retiring the route is decided after 2.4.0 ships, when the maintainer's sites are on WordPress 6.9 (the route also serves older sites).
- Network-wide actions on multisite beyond what core's own capabilities allow a network administrator to do through this site. Super-admin grants: never.
- Editing wp-config, PHP settings, files, .htaccess: never (master design).

## Anti-goals

- An update that cannot be undone because the copy failed silently. If the copy cannot be made, the update does not happen (unless the caller says so, see below).
- A plugin activation that takes the site down and stays down. Activation is checked and reverted.
- The plugin deactivating, deleting or rolling back itself, or an AI demoting the last administrator, or locking out the calling user.
- A result that says "the site is fine". It says what was checked.

## Switches

- Categories `users`, `plugins`, `themes`, `core` exist since 2.1.0 (read only so far). A new category **`email`** is added ("Email: send a test email to a site user or the admin address."). A category missing from the stored switches is off (fail-closed, since 2.1.0), so email starts off everywhere.
- Risky checkbox "Also allow risky actions" under Users, Plugins, Themes and Core, with the notes:
  - **Users:** "Can create users including administrators, change roles and emails, and delete users. A deleted user's content is reassigned, never deleted. Passwords are never set or shown; resets go by email."
  - **Plugins:** "Can install plugins from wordpress.org, activate, deactivate, update, roll back and delete them. A plugin change can take the site down; the previous version is kept for 30 days and a broken activation is reverted."
  - **Themes:** "Can install themes from wordpress.org, switch, update, roll back and delete them. Switching theme changes how the whole site looks; the previous version and the previous theme name are kept for 30 days."
  - **WordPress core:** "Can update WordPress itself. There is no rollback for a core update; keep a backup."
- Email has no risky switch (the only action is a test email to known recipients). Author's call: the master design listed "send email" as risky because it had arbitrary sending in mind; with the recipient rule below the category switch is the right gate.
- **Normal writes** (category on, risky not needed): `users-password-reset` (sends WordPress's own reset email, nothing else changes), `email-send-test`. Everything else that writes in 2.4.0 is risky.
- **The upgrade-consent step is repeated** ('3' -> '4', `d5b_abilities_consent_240`): the normal writes go live on update on sites whose master is on, and the note the admin agreed to in 2.3.0 did not mention email or users. Same mechanism, the notice names "send a test email, send password reset links, update translations and refresh the update list".
- The Updates switch is NOT required for any ability (as `cache-flush` in 2.3.0). The engine functions (`wpsu_*`) are always loaded; the switch gates the REST routes only.

## Abilities

Capabilities as core: `create_users`, `edit_users`, `promote_users`, `delete_users`, `list_users`; `install_plugins`, `activate_plugins`, `update_plugins`, `delete_plugins`; `install_themes`, `switch_themes`, `update_themes`, `delete_themes`; `update_core`; `manage_options` for the test email. On multisite the install, update, rollback and delete abilities need a network administrator (as core: those capabilities are network-only), and activate/deactivate work per site for plugins that are not network-activated.

### Plugins

| Ability | Risky | What it does |
|---|---|---|
| `plugins-status` | no (read, `update_plugins`) | `wpsu_status( false )`: installed, offered versions, blocked reasons, PHP and WordPress requirements, from the stored update list, never asking wordpress.org (a read must not change anything). Adds `kept_copies`: the plugins with a copy in the history store and the version kept. |
| `updates-check` | no (normal write, category `core`, `update_plugins`) | Clears the update caches and asks wordpress.org again for plugins, themes and core (`wpsu_status( true, true )`), as the route's POST `/refresh` does; returns the fresh status. History: a row with the counts (nothing to put back). Rate limit: one per 5 minutes per site (`too_soon`). |
| `plugins-install` | yes | By wordpress.org slug only (`plugins_api( 'plugin_information' )`, then `Plugin_Upgrader::install()` with the download link wordpress.org returns). A slug that already exists is refused (`exists`). Never activates. History: slug, version installed. |
| `plugins-activate` | yes | `activate_plugin()`; multisite `network: true` only for a network administrator. Then the page checks. **If the checks got worse, the plugin is deactivated again** and the result says `reverted: true` with the problems. A fatal on activation (the sandbox catches `activate_plugin`'s WP_Error) is reported as `activation_failed`. |
| `plugins-deactivate` | yes | `deactivate_plugin()`, page checks after. Not reverted automatically (a deactivation rarely breaks a page; raw shortcodes are for the human check). |
| `plugins-update` | yes | Keep a copy of the folder (below), then `wpsu_update( 'plugin', file, false )`, then the page checks. Input `rollback_on_failure` (default false): when true and the checks got worse, the kept copy is restored at once and the result says so. Default false because the maintainer first tries to fix things on the new version. |
| `plugins-rollback` | yes | Restores the kept copy named by its history row id (`history_id`) for that plugin file; refuses a row for another plugin, a row whose copy is gone, or a row older than the latest kept copy for that plugin unless `force_older: true`. The current folder is kept as the before of the rollback row. An active plugin stays active; page checks after. |
| `plugins-delete-preview` / `plugins-delete` | yes | Two steps with a confirmation code (2.2.0 mechanism). An active plugin is refused (`active`: deactivate first, on purpose, so the human sees the deactivation checks). The folder is copied to the history store, then `delete_plugins()`, which runs the plugin's uninstall routine (`uninstall.php` or the uninstall hook) and so drops the plugin's own tables and options. The preview says whether the plugin has one and, if so, "its data goes for good; only the files can be put back". With `keep_data: true` (same input on the preview, bound into the code) the files are removed without the uninstall routine (`delete_plugins()` cannot skip it: the handler removes the folder itself and clears the plugin caches), and the delete is fully undoable by putting the folder back. |

## The page checks (inside the plugin)

A port of the script's `pageHealth` / `compareHealth` to PHP, as `d5b_pages_check()`:

- Watched pages: the home page, the five most recently modified published pages, the newest published post (the script's default), at most 7, each fetched with `wp_remote_get` with a cache-buster query, `timeout => 15`, `sslverify` as the site's own loopback allows (`wp_remote_get` to `home_url` is what Site Health does; if the loopback fails before any update the result says `pages: unavailable` and the human check is the whole check).
- Per page: status, bytes, closed (`</html>` present), fatal text (the script's regular expression), title.
- Compare: a page that was already bad is not blamed; worse = status not 200, a fatal, cut off, or shrunk below half when it was over 2000 bytes.
- The before round is taken once per call, the after round once; both are in the result and in the history row (`pages.before`, `pages.after`, `pages.problems`).
- Time: 7 pages at up to 15 s is worst-case 105 s a round; the upgrader already sets 600 s. The builder sets a per-round budget of 60 s and marks unfetched pages `skipped`.

## Keeping a copy

- `d5b_keep_copy( kind, slug )` copies the plugin or theme folder (or a single-file plugin) to `uploads/d5b-history/<row id>-<hex>/<kind>/<slug>/` with `copy_dir()`, before the change, and the history row records `kept: { path, bytes, files }`.
- A copy over **512 MB** or a failed copy refuses the update or delete (`copy_failed`, with the reason) unless the caller passes `without_copy: true`; then the row says `kept: null` and the result repeats that the change cannot be put back by the plugin. Author's call: the default honours the 30-day rule; the escape hatch exists for a host with no disk space.
- **Total cap on the store: 2 GB** (`uploads/d5b-history` summed). At the cap an update, rollback or delete is refused (`store_full`, with the size and the oldest row's date); the plugin never deletes copies early to make room. The settings page history tab shows the store size.
- The 30-day prune (2.2.0) removes the row's files; today it removes plain files one level deep only, so it becomes **recursive** in 2.4.0 (a bug found in the builder check: a nested `<kind>/<slug>/` copy would otherwise stay for good), with the same safety: only under `d5b-history/<row id>-<hex>/`, never following symlinks.
- The store is closed to the web (2.2.0's rules) and copies of this plugin's own folder are never made because its own actions are refused.

## Guardrails (additions)

18. **Self-protection by construction:** `divi5-builder/divi5-builder.php` (and the legacy four) are refused for deactivate, delete, rollback and update through the abilities (`self`).
19. **Last administrator:** no role change or delete may leave the site without an administrator (counted fresh at run time, not from the read).
20. **Own account:** the caller cannot change their own role, delete themselves, or reset their own password through the abilities (use the normal screens).
21. **Install source:** the download URL must be the one `plugins_api` / `themes_api` returned for that slug and must be on `downloads.wordpress.org` over https; anything else is refused before the upgrader runs.
22. **Checked activations:** activate and switch theme are followed by the page checks and reverted when they got worse.
23. **Copy first:** no update or delete of a plugin or theme without the kept copy, unless `without_copy: true`.
24. **No passwords:** no ability input or output carries a password, key or reset link; the secret filter runs on every result as before.
25. **Email recipients:** only `me`, `admin` or an existing user.

## Tests

The 2.2.0 and 2.3.0 lists apply (history row with a rebuildable before, strictest switch, risky gate, capability matrix, secret rule, hostile input, mutation checks), plus:

- Page checks: each `pageHealth` and `compareHealth` case from `scripts/site-care/site-updates-test.js` ported to PHP against stubbed `wp_remote_get`; a loopback failure before = `unavailable`; the budget skips pages.
- Keep copy: the folder is copied before the upgrader runs (order asserted with a stub that records call order); over-cap refuses; `without_copy` proceeds with `kept: null`; a rollback restores byte-identical files and keeps the replaced folder.
- Activation revert: a stubbed `activate_plugin` plus a page round that turns fatal → `deactivate_plugin` called, `reverted: true`.
- Install: a non-wordpress.org download URL is refused before `install()`; an existing slug refused.
- Self-protection: every action on this plugin's file refused.
- Users: last administrator cases (delete, demote, via `users-update` and `users-delete`); own-account cases; role not editable; email in use; the password never appears in the result, the audit row or the history row (assert on the JSON of all three); `wp_new_user_notification` called with `'user'`; reset rate limit; meta deny-list.
- Email: each recipient form; an arbitrary address refused; `wp_mail_failed` message captured; the rate limit.
- Plugin delete: with an uninstall routine the preview says so and `delete_plugins()` is called; with `keep_data` the routine is not run (assert `uninstall_plugin` not called) and the folder is removed; the code binds `keep_data` (a code taken with one value is refused with the other).
- Store cap: at 2 GB the write is refused before the upgrader runs; the prune removes nested folders and does not follow a symlink.
- `updates-check`: `plugins-status` never clears a transient (assert on a stub); `updates-check` does, once, and is rate-limited.
- Core: the version must be one offered; no copy is attempted; the result's `rollback` text.
- Live script `scripts/abilities-live-maint.js <site> <plugin|theme-switch|update|user|email|history|all> [--confirm go]` (exit codes as the 2.3.0 script): `plugin` installs `hello-dolly` from wordpress.org, activates (checks), deactivates, deletes with preview and code, and asserts the kept copy row; `update` updates the first plugin with a waiting update whose slug the maintainer passes with `--item`, then rolls it back, and skips with a note when nothing is waiting; `user` creates `d5b-live-user`, resets its password (the script checks only the result, no inbox), changes its role to author, deletes it reassigning to the caller; `email` sends to `me`; `history` checks that every write has its row and every update/rollback row has `kept`.
