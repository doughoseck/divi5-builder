# Abilities 2.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release 2.3.0 of the `divi5-builder` plugin: site-management write abilities (settings, homepage, theme mods, Custom CSS, widgets, cache flush, cron run, templates and global styles on block themes) and the first risky switches.

**Architecture:** Every write is a definition through the 2.2.0 helpers (`d5b_wc_def`, `d5b_wc_history`, the secret and key rules), registered under the existing categories. One new flag, `risky => true`, is read by the registration gate, the permission callback and the run wrapper, and backed by the `risky_on` value the switch store already holds. New files `write-settings.php`, `write-appearance.php`, `write-widgets.php`, `write-site.php` and `write-templates.php` under `inc/abilities/`. The cache flush and nothing else touches `parts/updates.php`, by calling `wpsu_clear_caches()`.

**Tech Stack:** PHP 7.4+ WordPress plugin, WordPress Abilities API (6.9+), the plugin's PHP test harness (`scripts/plugin-test-stubs.php`), Node for the live script.

**Spec:** `docs/superpowers/specs/2026-10-30-abilities-2.3.0-design.md` (extends the master design and the 2.2.0 design).

## Global Constraints

- Plugin version `2.3.0`; `D5B_DB_VERSION` `'3'` (no new table; the bump drives the consent step).
- A def with `risky => true` is registered only when master, category and the category's `risky_on` are all on; `d5b_ability_permit()` and `d5b_ability_run()` re-check all three.
- Risky switches start off on every site, including upgrades.
- Upgrade `'2' -> '3'` on a site whose master is on: master off once (network-wide on multisite, as 2.2.0 does via the consent option), notice text verbatim from the spec's "Switches" section.
- Capabilities: `manage_options` for settings, homepage, theme mods, templates, global styles, cache, cron; `edit_css` for Custom CSS; `edit_theme_options` for widgets; on multisite `cache` and `health` also need `manage_network`.
- `siteurl`, `home`, `admin_email` are never writable; the settings allow-list is exactly: normal `blogname`, `blogdescription`, `date_format`, `time_format`, `start_of_week`, `posts_per_page`, `default_comment_status`; risky `timezone_string`, `gmt_offset`, `WPLANG`, `permalink_structure`, `blog_public`.
- The one rule: every write has a history row whose `before` holds the full previous value (or `absent: true`); theme-mod delete and widget remove are normal writes whose row is the copy.
- The 2.2.0 rules apply unchanged: ASCII key rule and case check for names, the secret rule (`d5b_wc_secret_free`, `d5b_wc_secret_error`), `masked_read`, `audit_args`, content keys and raw_paths, error codes and statuses, no em dashes, no client or site names in public files, stand-ins faithful to core.
- Cron: only scheduled events, identified exactly; `d5b_*` hooks refused; `doing_cron` lock; reschedule or unschedule BEFORE running, as `wp_cron()` does; measure and report (`over_budget` past 20 s), never kill.
- Every new PHP file in the loader's explicit list in the same commit; inc files only define functions.

## Review Focus

1. A site with the master on upgrading from 2.2.0: no settings or widget write must be possible before an admin ticks the master again (Task 1 tests the consent step at `'2' -> '3'`).
2. `settings-set` with `permalink_structure` on a site whose `.htaccess` is not writable: the option changes, rewrite rules are flushed, and the response says whether the flush could write the file (Task 2 tests the flag).
3. `widgets-remove` on a block widget holding a 100 KB block: the row holds the whole instance and `sidebars_widgets` map, and a hand restore from the row is possible (Task 4 rebuild test).
4. `cron-run` on a recurring event while real WP-Cron fires at the same moment: the lock refuses one of them; no double run (Task 5 lock test).
5. `appearance-custom-css-set` with an empty `css` after someone pasted a 200 KB stylesheet in the Customizer: the hash check refuses with `stale`; with the right hash the empty write succeeds and the row holds the 200 KB (Task 3).
